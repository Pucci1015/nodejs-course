# ADR 0001: 技術の選び方

- 状態: 決定（2026-11-19）
- 決めた人: 第13部の作者

## 文脈

会議室の予約を、小さなチームで作り、PaaS に公開する。作る人は、第5〜12部で Express + React（Vite）のタスク管理アプリを作り、第9部で Next.js も使った。期間は4章分（実装は2章）と短い。

## 考えた選択肢

| 選択肢                                             | よい点                                                                                              | 困る点                                                                                                                  |
| -------------------------------------------------- | --------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| A. Express + React（Vite）。第12部の土台から始める | ログイン・設定・仕事の列・監視・Docker・CI が、もう動いてテストもある。API を画面と別に確かめられる | 画面と API の2つのパッケージ                                                                                            |
| B. Next.js（第9部）                                | 1つのパッケージ。サーバで描く                                                                       | 土台のログイン・仕事の列・SSE を作り直す。Cache Components と、人ごとの表・SSE の組み合わせを、新しく確かめる必要がある |
| C. 予約の SaaS を使う                              | 作らなくてよい                                                                                      | 学ぶための題材にならない                                                                                                |

## 決定

**A** を選ぶ。決め手は「期間が短く、土台が動いている」こと。中心の機能（予約の決まりと重なり）に時間を使う。

- データベースは PostgreSQL。重なりを EXCLUDE 制約で守れる（MySQL・SQLite にはこの制約が無い）
- リアルタイムは SSE（第27章）。知らせはサーバからの一方向だけなので、WebSocket は要らない。台をまたぐのは Redis の Pub/Sub（第66章 7節）
- 決まった時刻の仕事（前日のリマインド）は BullMQ の `upsertJobScheduler`（第64章 6節）
- ファイルの保存（第63章）は使わない（要件に無い）

## 結果

- よくなること: 土台のテスト（API 25・画面 14・E2E 1）が最初から通る。第12部の Dockerfile・compose・render.yaml を出発点にできる
- 気をつけること: 画面と API で、予約の形（`Booking`）を2か所に書く（API の Zod と画面の Zod）。形を変えたら両方を直す
