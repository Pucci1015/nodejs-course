# test — 外から HTTP で確かめるテスト

| ファイル | 中身 |
| --- | --- |
| [api.test.ts](api.test.ts) | 30 個のテスト（1〜25 は第5部と同じ、26〜30 は第6部で足したもの）。第7部で、第6部の `api.test.mjs` を TypeScript にした（確かめることは同じ。ポートだけ変えた）。サーバを別のプロセスで起動し、`fetch` だけで確かめる |

```sh
$ npm test                                          # 完成例を確かめる
$ API_SERVER=../../task-api/src/server.ts npm test   # 別の場所のサーバを確かめる（test/ から見たパス）
```

- 応答の JSON は `any` のまま読み、`assert` で確かめます（ファイルの最初の `TestResponse` 型）。そのため `eslint.config.js` で、`test/` だけ `no-unsafe-…` のルールを止めています
- PostgreSQL が要ります。先に `~/dev/part06` で `docker compose up -d --wait` を動かしておきます。つなぎ先は、データベース `taskapi`（`TEST_DATABASE_URL` で変えられる）です
- テストは、起動するサーバごとに、`taskapi` の中に新しいスキーマ（`test_` で始まる名前）を作り、`DATABASE_SCHEMA` で渡します。サーバは、そのスキーマにマイグレーションを動かしてから始まるので、最初は空です。テストが終わると、スキーマごと消します（`npm start` で使う `public` のテーブルには触りません）
- サーバは `127.0.0.1:9491` で起動します。テスト 23・24・28〜30 は、別のサーバを `9492` で起動します。ほかのものがこのポートを使っていると、失敗します
- テストは上から順に動き、同じサーバのデータを使い続けます。1つだけ動かしたいときは、`node --test --test-name-pattern='SSE' "test/*.test.ts"` のようにします（ただし、前のテストで作ったデータが無いと失敗するものもあります）
- テストは、中の作り（どのファイルに何を書いたか）を見ません。第5・6部の成果物の要件だけを確かめるので、自分の API にもそのまま使えます（第28章 6節の契約のテスト）
