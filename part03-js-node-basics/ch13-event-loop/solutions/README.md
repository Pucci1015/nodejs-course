## 問題1 表示される順番を予想する

```
$ node predict-loop.mjs
A
P
L
N
I
O
M
K
J
E
H
B
C
D
F
```

| 段階 | 表示 | 理由 |
| --- | --- | --- |
| `readFile` のコールバック（poll のフェーズ） | `A`、`P` | 同期のコードを最後まで実行する。タイマー・immediate・nextTick・マイクロタスクは予約されるだけ |
| コールバックの直後: nextTick の待ち行列 | `L`、`N` | I/O のコールバックの後は、まず nextTick を空にする。`L` の中で足した `N` も、同じ待ち行列なので続けて実行される。`L` の中で足した `M` はマイクロタスクなので、後回し |
| 次にマイクロタスク | `I`、`O`、`M`、`K` | 予約された順に `I`、`O`、`M`。`I` が終わると、次の `then`（`K`）が待ち行列の最後に入る |
| マイクロタスクの後、また nextTick | `J` | `I` の中で足した `J` は、マイクロタスクを空にした後に、もう一度 nextTick の待ち行列を見たときに実行される |
| check のフェーズ | `E`、`H` | poll の次は check。`E` の後、nextTick の `H` |
| 次の周の timers のフェーズ | `B`、`C`、`D` | `B` の後、nextTick の `C`、マイクロタスクの `D`（コールバックの中なので nextTick が先） |
| 同じか次の timers のフェーズ | `F` | `E` の中で予約した 1ms のタイマー。`B` より後に予約したので、`B` より後 |

いちばん間違えやすいのは `L`・`N` と `I` の順番と、`J` の位置です。「コールバックが1つ終わるたびに、**nextTick を空にしてから**マイクロタスクを空にし、マイクロタスクの中で nextTick が足されたら、またそれを空にする」と覚えてください。

### 追加の問い1: G の位置

20回実行した結果の例です。

```
     13 APLNIOMKJEHBCDGF
      5 APLNIOMKJEHGBCDF
      2 APLNIOMKJEHBCDFG
```

`G` は `E` の中で予約した setImmediate なので、**次の周の** check のフェーズで実行されます。一方、`B` のタイマーは `readFile` のコールバックの中で予約した 1ms のタイマーです。

- check（`E`）の後、次の周の timers に来たとき、`B` の 1ms が**過ぎていれば** `B` が先に実行され、その周の check で `G`
- **まだ過ぎていなければ**、timers では何もせずに poll → check に進むので、`G` が `B` より先になる

`F` と `G` の順番も同じ理由で変わります。setTimeout と setImmediate の順番は、I/O のコールバックの中で**同時に予約したときだけ**決まっていて、それ以外は時間しだいです。順番が大事な処理を、この違いに頼って書いてはいけません。

### 追加の問い2: 一番外側に書いたら

```
APIOKLJNMEHBCDF   （または APIOKLJNMBCDEHF）
```

2つのことが変わります。

- ES モジュールの一番外側では、**マイクロタスクが nextTick より先**になる（本文3.3節）。`I`、`O`、`K` の後に `L`、`J`、`N`、`M`
- poll のフェーズの中ではないので、`B`（タイマー）と `E`（immediate）の順番が決まらない

## 問題2 重い計算で止まるサーバを、Worker で直す

[report-server.mjs](report-server.mjs) と [report-worker.mjs](report-worker.mjs) を見てください。`// 修正:` と `// 追加:` のコメントが付いた所が変えた場所です。

ポイントです。

- **Worker を Promise で包む**: `message` で resolve、`error` と「`message` の前の `exit`」で reject します。`resolve` と `reject` は最初の1回だけが有効なので、`message` の後に来る `exit(0)` は無視されます
- **ハンドラを `async` にして `await`**: 計算を待っている間、メインのスレッドは空いているので、`/health` にすぐ応えられます
- **`finally` で枠を返す**: 成功しても失敗しても `runningJobs--` します。`try` の中だけで減らすと、失敗したときに枠が減らず、やがて全部のリクエストが 503 になります
- **`503` と `Retry-After`**: 「今は無理だが、少し後なら大丈夫」という意味です。第12章 練習問題6の `retry` のようなクライアントは、503 を受け取ったらやり直します

リクエストのたびに Worker を起動しているので、1回あたり数十 ms の余計な時間がかかります。本番では、起動しておいた Worker を使い回す **Worker プール**（`piscina` などのパッケージ）を使うのが一般的です。

「考えてみよう」の答え: 順番待ちにすると、少しの混雑なら全員に答えを返せます。ただし、待ち行列に上限が無いと、混雑が続いたときに待ち行列がどこまでも伸び、メモリを使い果たしたり、クライアントがとっくにあきらめたリクエストを計算し続けたりします。順番待ちにするなら、「待ち行列の長さの上限」と「待ち時間の上限（超えたら 503）」を必ず決めます。これは、第12章の `mapLimit` を、サーバ全体で共有する形にしたものと考えられます。

## 問題3 重い処理を小分けにして、合間に譲る

[chunked.mjs](chunked.mjs) を見てください。

- **`setImmediate` で譲る**: `new Promise((resolve) => setImmediate(resolve))` を `await` すると、続きはタスクの待ち行列に入ります。その前に、溜まっていたタイマーや I/O のコールバックが実行されます
- **最初にも譲る**: 「呼んだ時点では処理しない」を満たすためです。`async` 関数は最初の `await` までを同期で実行するので（第12章4.2節）、最初に `await` しないと、1つ目の区切りまでは呼んだ側のコードの中で処理されてしまいます
- **時間で区切る**: `performance.now()` で「この区切りを始めた時刻」を覚え、`budgetMs` を超えたら譲ります。1000件ごと、のように件数で区切ると、1件が重いときにイベントループを長く止めます

`await Promise.resolve()` に変えると、次の3つが失敗します。

- 「処理の途中でも、タイマーが動ける」: マイクロタスクは、タイマーより先に**すべて**片付けられます。処理が全部終わるまで、タイマーの順番は来ません
- 「budgetMs を大きくすると、譲る回数が減る」: 1回も譲っていないので、どちらも 0回になります
- 「signal で中止したら…」: 中止するタイマー（30ms 後）が、処理が全部終わるまで動けません

`node:timers/promises` には、譲るための `scheduler.yield()` もあります（執筆時点では実験的な機能です。使う前に Node.js のドキュメントで状態を確かめてください）。

## 問題4 スレッドプールが埋まると何が待たされるか

作成時に、4コアの Linux で実行した結果です。Mac では数字が変わりますが、傾向は同じになるはずです。

| ハッシュの数 | スレッドプール | ファイル | 名前解決 | タイマー |
| --- | --- | --- | --- | --- |
| 3 | 4 | 3ms | 3ms | 10ms |
| 4 | 4 | 508ms | 508ms | 10ms |
| 8 | 4 | 947ms | 948ms | 12ms |
| 4 | 8 | 19ms | 1ms | 10ms |

1. **タイマー**は、スレッドプールを使いません。タイマーはイベントループ自身が管理していて、メインのスレッドは空いている（ハッシュは裏のスレッドで計算している）ので、予定どおり動きます
2. スレッドプールは4本です。ハッシュが **4件**だと4本とも埋まり、ファイルの読み込みと名前解決は、どれかのハッシュが終わってスレッドが空くまで待たされます。**3件**なら1本空いているので、すぐに処理されます。8件のときは、前の4件が終わった後、ファイルと名前解決が、残りのハッシュ（5〜8件目）と同じ待ち行列に並ぶので、さらに待たされます
3. `fetch` は、接続の前に `dns.lookup` でホスト名を IP アドレスにします。スレッドプールが埋まっていると、**通信そのものは OS が待つのに、名前解決で待たされる**ことになります。「外の API へのリクエストが、なぜか数百 ms 遅い」という症状の原因になります
4. 防ぐ方法:
   - **`UV_THREADPOOL_SIZE` を増やす**: 簡単。ただし、CPU のコアの数より多く計算しても速くはならず、メモリも使う。根本的な解決ではない
   - **ハッシュの計算を Worker や別のプロセスに移す**: ファイルや DNS の処理と、スレッドを取り合わなくなる。ただし、仕組みが複雑になる
   - **同時に計算するハッシュの数を制限する**（第12章の `mapLimit` の考え方）: スレッドプールに必ず空きを残せる。ただし、ログインが多いと待ち時間が伸びる
   - **ログインの回数を制限する**（レート制限。第10部）: 総当たりの攻撃への対策にもなる

## 問題5 正規表現でサーバが止まる（ReDoS）

1. 長さが2増えるごとに、約4倍になります（2倍ずつ増えていく「指数関数的」な増え方です）。長さ 29 で約 3秒なので、長さ 41 なら 3秒 × 4⁶ ≒ 12,000秒、**約3時間半**です。
2. `([a-z0-9]+-?)*` は、`aaaa` を「`aaaa`」「`aaa` + `a`」「`aa` + `aa`」「`a` + `a` + `aa`」… のように、何通りにも分けて表せます（ハイフンが省略できるため）。n 文字なら約 2ⁿ 通りあります。最後の `!` で失敗すると、正規表現のエンジン（JavaScript のエンジンの多くは**バックトラック**方式）は、「分け方を変えれば成功するかもしれない」と考えて、**すべての分け方を試してから**失敗を返します。
3. [slug.mjs](slug.mjs) の `/^[a-z0-9]+(?:-[a-z0-9]+)*$/` は、「英数字の並び」の後に「ハイフン + 英数字の並び」が0回以上、という形です。英数字の並びの区切りは**必ずハイフン**なので、文字列の分け方は1通りしかありません。失敗するときも、試すことはほとんどありません。

```sh
$ node redos-measure.mjs ../solutions/slug.mjs
長さ  17:      0.1ms（結果 false）
...
長さ 101:      0.0ms（結果 false）
```

危ない正規表現の見分け方の目安は、「**繰り返しの中に、繰り返しがある**」（`(a+)*`、`(a|aa)+`、`(\w+\s?)*` など）で、しかも「**同じ文字列を、内側と外側のどちらの繰り返しでも表せる**」ものです。

ほかの対策:

- **入力の長さを先に制限する**: 模範解答でも 100 文字で断っています。ただし、上の例では長さ 41 でも何時間もかかるので、長さの制限だけでは守れません
- **ESLint のプラグイン**（`eslint-plugin-regexp` など。第11部）で、危ない正規表現を見つける
- **正規表現を使わない**: 単純な形なら、1文字ずつ調べる関数の方が読みやすいこともあります
- V8 には、バックトラックしない正規表現のエンジンを使う実験的なオプション（`--enable-experimental-regexp-engine` と `l` フラグ）もあります。執筆時点では実験的な機能なので、使う前にドキュメントで状態を確かめてください

## 問題6 イベントループの見張りを作る

[lag-monitor.mjs](lag-monitor.mjs) を見てください。

- `setInterval` のコールバックの中で、前に呼ばれた時刻との差から `intervalMs` を引いたものが「遅れ」です。イベントループが 200ms 止まると、次のコールバックは約 200ms 遅れて呼ばれます
- 時刻には `Date.now()` ではなく **`performance.now()`** を使います。`Date.now()` は Mac の時計の合わせ直し（NTP）で前後に飛ぶことがありますが、`performance.now()` はプロセスの起動からの経過時間で、戻ることがありません
- **`timer.unref()`** で、見張りのタイマーがプロセスを引き止めないようにしています（本文8節）。これが無いと、見張りを入れたプログラムが、`stop()` を呼ばない限り終わらなくなります
- 200ms 止まっても、`onLag` は1回だけ呼ばれます。止まっている間に予定されていた約10回のコールバックは、止まっている間は呼ばれず、再開したときに**1回だけ**呼ばれるからです（`setInterval` は、遅れた分をまとめて取り返そうとはしません）

`report-server.mjs`（直す前）に見張りを入れると、`/report?n=5000000` のたびに `イベントループが 1274ms 止まった` のような警告が出ます。Worker で直した後は出ません。本番では、この警告をログに出すだけでなく、数を数えて監視の仕組みに送ります（第12部）。
