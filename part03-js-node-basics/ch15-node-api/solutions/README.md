## 問題1 path と Buffer の結果を予想する

```
$ node predict.mjs
 1: "/srv/app/uploads/a.png"
 2: "/srv/app/etc/passwd"
 3: "/etc/passwd"
 4: "/etc/passwd"
 5: "memo.txt"
 6: ".JPG"
 7: ""
 8: "img/a.png"
 9: "../secret.txt"
10: "a/b"
11: "../b"
12: 2
13: 3
14: "4/2"
15: "hello"
```

| | 理由 |
| --- | --- |
| 1 | `public/../uploads` の `..` が `public` を打ち消す |
| 2・3 | `join` は、すべての部分を `/` で**つなぐ**だけ。`/etc/passwd` の先頭の `/` も「区切り」として扱う。`resolve` は、右から見て**絶対パスになった所**から先だけを使う（`cd /srv/app` してから `cd /etc/passwd` したのと同じ） |
| 4 | `..` が多すぎると、`/` より上には行けないので `/` で止まり、`/etc/passwd` になる。**公開するフォルダの外に出てしまった** |
| 5 | 最後の `/` は無視される |
| 6・7 | 大文字・小文字はそのまま（比べるときは `toLowerCase()` する）。`.` が無ければ空文字列 |
| 8・9 | `relative` の結果が `..` で始まれば、`to` は `from` の**外**にある。9 は公開するフォルダの外を指している |
| 10 | 空の部分は無視される |
| 11 | 相対パスのまま `..` が残る（`resolve` と違って、今のフォルダを使わない） |
| 12・13 | 12 の `é` は1つの文字（U+00E9、NFC）で、UTF-8 で2バイト。13 は `e` + 合成用のアクセント記号（U+0301、NFD）の2文字で、1 + 2 = 3バイト。見た目は同じ |
| 14 | `😀` は UTF-8 で4バイト、JavaScript の文字列では UTF-16 の2単位（サロゲートペア）なので `length` は 2 |
| 15 | 16進数の文字列をバイト列にして、UTF-8 として読んだ |

4と9から分かるように、`path.join(root, 利用者の入力)` は、入力に `..` があると `root` の外を指します。`path.relative(root, 結果)` が `..` で始まる（か、絶対パスになる）なら外を指している、と判断できます。ただし、シンボリックリンクや、URL のパーセントエンコード（`%2e%2e%2f`）、`\0` など、気を付けることは他にもあるので、第4部 第19章でまとめて扱います。

12・13 は、Mac で実際に起きる問題です。macOS のファイルシステムは、ファイル名を NFD に近い形で返すことがあり、`'café.txt' === ファイル名` が `false` になることがあります。名前を比べる前に、両方を `normalize('NFC')` すると安全です。

## 問題2 途中で落ちても壊れない書き込みと、取りこぼさない更新

[atomic.mjs](atomic.mjs) を見てください。

### writeFileAtomic

- 一時ファイルの名前は、`.<名前>.<乱数>.tmp`。先頭の `.` で隠しファイルにし、乱数で同時に書いてもぶつからないようにしています。`flag: 'wx'` で開くので、万一同じ名前があっても、他人のファイルを上書きしません
- `FileHandle`（`fs.open` の戻り値）を使うのは、`sync()`（fsync）を呼ぶためです。`writeFile` が終わっても、内容はまだ OS のメモリ（ページキャッシュ）にあるだけかもしれません。その状態で `rename` し、直後に電源が落ちると、「名前は新しいのに中身は空」というファイルが残ることがあります
- `catch` の中で `handle?.close()` と `fs.rm(tmp, { force: true })` をしてから投げ直します。`force: true` は、一時ファイルがまだ作られていなかったときも、エラーにしないためです
- `fsync` は、ディスクに書き終わるまで待つので遅くなります。たくさんの小さな書き込みでは、`fsync: false` にする判断もあります

### updateJson

同時に呼ばれたものを1つずつ動かすため、ファイルごとに「最後の更新の Promise」を `Map` に覚えておき、次の更新はその後ろにつなぎます（`previous.then(run, run)`）。

- `then(run, run)` と、成功・失敗のどちらでも `run` するのは、前の更新が失敗しても、次の更新を止めないためです
- `Map` に入れるのは、失敗を飲み込んだ `tail` の方です。`current`（失敗するかもしれない）をそのまま入れると、使う人が `catch` していても、`Map` の中の Promise が unhandled rejection になりえます
- 自分が最後なら `Map` から消します。消さないと、使ったファイルの数だけ `Map` が大きくなり続けます
- キーは `path.resolve(file)` にしています。`./data.json` と `data.json` を同じファイルとして扱うためです

`structuredClone(defaultValue)` でコピーしているのは、`updater` が受け取った値を書き換えたとき、`defaultValue` そのもの（次の呼び出しでも使う）が変わってしまわないようにするためです（第11章8節）。

### 考えてみよう

1. `rename` が一瞬で置き換えられるのは、**同じファイルシステムの中**だけです。`os.tmpdir()` が別のディスク（ボリューム）にあると、`rename` は `EXDEV` のエラーになります。コピーして消す方法に切り替えると、その間はアトミックではありません。
2. `updateJson` の順番待ちは、そのプロセスのメモリの中にある `Map` です。別のプロセスは、その `Map` を見られません。プロセスをまたいで守るには、**ロックファイル**（`flag: 'wx'` で `data.json.lock` を作れた人だけが更新し、終わったら消す。作れなければ少し待ってやり直す）や、OS のファイルロックを使います。ロックを持ったままプロセスが落ちたときの扱い（古いロックを見分ける）まで考える必要があり、難しい問題です。データを複数のプロセスから更新するなら、データベース（第6部）を使うのが普通です。
3. 起動したときに、`.<名前>.*.tmp` に当てはまるファイルで、**作られてから十分に時間がたったもの**（たとえば1時間以上前の `mtime`）を消します。今まさに別のプロセスが書いている一時ファイルを消さないよう、時間で区別します。

## 問題3 バイトのチャンクを1行ずつにする Transform

[lines.mjs](lines.mjs) を見てください。

- **文字の境目**: `TextDecoder` の `decode(chunk, { stream: true })` は、文字の途中で切れたバイトを内部に持っておき、次のチャンクとつなげて文字にします。最後に `decode()`（引数なし）を呼ぶと、持っておいたバイトを吐き出します。途中で入力が終わっていれば、`fatal: true` なのでエラーになります
- **行の境目**: 変換した文字列を `\n` で `split` し、**最後の要素だけ**は「まだ改行が来ていない、行の途中」として `rest` に残します。次のチャンクの先頭とつながります
- **`\r` と `\n` が別のチャンク**: `a\r` と `\nb` に分かれても、`\r` は `rest` の最後に残り、次のチャンクの `\n` で行が終わったときに、`endsWith('\r')` で取られます
- **長すぎる行**: `rest` の長さも確かめるのが大事です。改行の無いデータが送られ続けると、`lines` には何も入らず、`rest` だけが大きくなっていきます
- **`flush`**: 入力が終わったときに呼ばれます。ここで最後の行（改行で終わっていない行）を出します

「考えてみよう」の答え: 上限が無いと、改行を送らずにデータを送り続けるだけで、`rest` が大きくなり続け、サーバのメモリを使い果たします（第13章の ReDoS と同じく、少ない手間でサーバを止められる DoS）。外から来るデータを読むときは、「1行の長さ」「全体の大きさ」「かかる時間」に、必ず上限を付けます。第4部 第20章で、リクエストのボディにも上限を付けます。

## 問題4 大きなログ（.gz も）を少しずつ集計する

[log-stream.mjs](log-stream.mjs) を見てください。

- **.gz**: `fs.createReadStream(file).pipe(zlib.createGunzip())` の後ろに `readline` をつなぎます。`pipe` は読む側のエラーを伝えないので、`input.on('error', (err) => gunzip.destroy(err))` で伝えています。これが無いと、無い `.gz` を渡したときに `ENOENT` が `for await` に届かず、プロセスがエラーで終わってしまいます。`pipeline` を使えばこの心配は無いのですが、`readline` には「Readable」を渡す必要があるため、ここでは `pipe` を使っています
- **少しずつ集計する**: 行を配列に溜めず、1行ごとに数を足すだけにしています。メモリに残るのは、パスごとの数（`Map`）と、いくつかの数だけです
- **first と last**: 第11章の模範解答は、全部の時刻を配列にしてから `Math.min(...times)` で求めていました。スプレッド構文（`...`）は、配列の要素を**関数の引数**として渡すので、要素が十数万を超えると、引数がコールスタックに載り切らず、`RangeError: Maximum call stack size exceeded` になります。1件ずつ比べれば、件数に関係なく動きます
- **壊れた .gz**: gunzip が途中でエラーを出すと、`for await` が例外を投げるので、途中までの集計を返さずに rejected になります

「できたら」の答え: 第11章の `summarize` は、15万行で `RangeError: Maximum call stack size exceeded` になります。上のとおり、`Math.min(...times)` のせいです。小さなデータで正しく動くコードが、大きなデータで壊れる典型的な例です。`reduce` や `for` で1件ずつ比べるように直します。

## 問題5 EventEmitter で進み具合を知らせる仕事の列

[job-queue.mjs](job-queue.mjs) を見てください。

- **`super()`**: EventEmitter を継承したクラスでは、コンストラクタの最初で `super()` を呼びます（第11章5節）
- **すぐに始めない**: `add` の中ですぐに仕事を始めると、`start` が `add` の中で（同期で）emit されます。`add` を呼んだ後に `on('start')` を付けた人は、それを聞き逃します（`emit` は同期で、登録されていないリスナーは呼ばれないため）。`queueMicrotask` で、`add` を呼んだ側の同期のコードが終わってから始めます
- **同期で投げる仕事**: `Promise.resolve().then(() => job.fn())` で包むと、`fn` が同期で例外を投げても、`failed` として扱えます
- **`idle` と `onIdle()`**: 全部終わった時点で `idle` を emit し、`onIdle()` は `events.once(this, 'idle')` で待ちます。今すぐ空なら、待たずに終わります（待つと、もう来ない `idle` を永遠に待つことになる）
- **`#` のプライベートなフィールド**: 外から `#running` などを書き換えられないようにしています

考えてみよう:

1. `'error'` のリスナーが無いと、`emit('error')` は例外を投げます。仕事の失敗のたびに、列の中の処理（`then` の中）で例外が投げられ、unhandled rejection でプロセスが終わったり、`#running--` が実行されずに列が止まったりします。使う人に「必ず `error` のリスナーを付けてください」と求めるより、ふつうに起きる失敗には別の名前（`failed`）を使う方が安全です。
2. 仕事が失敗すると、`add` が返した Promise が rejected になり、誰も `catch` していなければ unhandled rejection でプロセスが終わります。対策として、「`add` は Promise を返さず、結果はイベントだけで知らせる」「結果の Promise が欲しい人だけが使う、別のメソッド（`addAndWait` など）を用意する」といった設計があります。どちらが良いかは使い方しだいですが、「Promise を返すなら、使う人が `catch` する責任を持つ」ことは、ドキュメントに書いておくべきです。

## 問題6 フォルダの大きさを数える（du の小さな版）

[dir-size.mjs](dir-size.mjs) を見てください。

- **リンクをたどらない**: `readdir` の `withFileTypes` の `isSymbolicLink()` で見分け、数えるだけにします。大きさは `lstat`（リンクそのもの）で取ります。`stat` を使うとリンクの先をたどるので、輪になったリンク（`sub/loop → ..`）で終わらなくなったり、同じファイルを2回数えたりします
- **同時に開く数の制限**: `createLimiter` は、「関数を渡すと、空きができてから呼ぶ」関数を作ります。`readdir` と `lstat` を、すべてこれを通して呼びます。第12章の `mapLimit` は「配列の全部に同じ関数を適用する」形でしたが、ここでは、フォルダをたどりながら、次々に新しい呼び出しが増えるので、1回ずつ制限できる形にしています
- **ただし、`walk` の中で `walk` を待つ**: 下のフォルダの `walk` は、制限の**外で**呼んでいます。`walk` そのものを制限の中で呼ぶと、親のフォルダの `walk` が枠を持ったまま子の `walk` を待ち、深いフォルダで枠が足りなくなって、全体が止まります（デッドロック）
- **読めないフォルダ**: `readdir` の失敗を `errors` に記録して、そのフォルダだけを飛ばします。最初の `root` だけは、呼んだ人の間違いなので、例外にします
- **`formatBytes`**: `1024` で割り続け、B のときだけ整数のまま、それ以外は小数第1位まで表示します

`node dir-size.mjs ~/dev` は、中のフォルダ・ファイルごとの大きさを大きい順に表示します。`du -sh ~/dev/*` の結果と比べてみてください。`du` は、ファイルの大きさではなく、ディスクの上で**使っている領域**（ブロックの数）を数えるので、小さなファイルがたくさんあると、`du` の方が大きくなります。

「考えてみよう」の答え: 同時に何万ものファイルを開こうとして、OS の上限（`ulimit -n`。Mac の既定は 256 などの小さな値のことがある）を超え、`EMFILE` のエラーが出ます。また、fs の非同期の処理は libuv のスレッドプール（第13章4節）で動くので、何万もの処理を頼んでも、同時に動くのは4つです。待っている処理がメモリに溜まるだけで、速くはなりません。
